# Project context

Source-verified navigation notes; inspect current implementation before edits. Existing README descriptions and verification claims are not substitutes for running checks. No application tests were run during this documentation-only context ingestion.

## Entry points and boundaries

- `src/main.ts` bootstraps the standalone workspace using `app.config.ts` and lazy `app.routes.ts` (configuration list, editor, preview, dev-only tools).
- `main.elements.ts` is a side-effect-free dynamic-import facade. `main.storefront.ts` registers `<zb-product-customizer>`; `main.admin.ts` registers `<zb-personalization-admin>`. Both guard registration globally, run zoneless, and support a host CSP nonce. Do not install host-wide error listeners in embedded applications.
- `scripts/finalize-element.mjs` builds stable `storefront.js` / `store-admin.js` entries, declarations, integration demos, manifest and compatibility shim, enforcing entry download budgets and excluding admin code from the storefront graph. Deployable output is `dist/product-personalization/`.
- Both elements use Shadow DOM. Admin routes use `MemoryLocationStrategy` and `NoTitleStrategy`, preserving host URL/history/title. Repeated assignments of `view` / `config-id` are navigation commands handled by the registration wrapper. Multiple admin instances share a session; shopper drafts are isolated per element.
- Contract types live in `customizer/models/element-contract.ts`, `admin-element-contract.ts`, and `events.models.ts`; integration examples are under `integration-demo/` and browser hosts under `tests/browser/host/`.

## Configuration and rendering

- `customizer/models/product.models.ts`: schema v2 `ProductConfig` links variants → mockups / enabled printable areas → artwork options → layers → explicit `fieldId` bindings. Layer array order is back to front. Schema v1 is validated then upgraded by `config-upgrade.ts`; retain source schema for compatible output snapshots/events.
- Each printable area has independent production canvas pixels and a rect/ellipse/path mask. Layers use those pixels, clockwise rotation around their center. Mockup placements are normalized against the natural photo dimensions, supporting rectangles or perspective quads. Shape paths use their own viewBox. Never persist editor zoom/display coordinates as production geometry.
- `util/resolve.ts` resolves variants, areas, visible layers, active fields, declarative conditions and form grouping. Inactive field values remain in local state for switching back, but are excluded from rendering, validation and saved snapshots. `visible: false` fields can remain active without an input. Hidden mockups are skipped with a first-assigned fallback if all are hidden.
- `util/scene.ts` evaluates scenes, field errors, text fitting/glyphs, crops and effective resolution. `services/render.service.ts` + `util/draw.ts` render Canvas 2D for editor, customer preview and export. Reuse this pipeline; SVG selection handles/boundaries are editor aids, not production output.
- `ExportService` produces one masked production PNG per active area, composite PNG per applicable mockup, serializable customization JSON and canonical uploaded image blobs. First artwork/preview blobs remain compatibility aliases. JSON carries asset ids, never image bytes or blob URLs; display prices are explicitly non-authoritative.

## Shopper lifecycle

- `product-customizer.component.ts` orchestrates inputs/effects, loading, public resolution, events and export. Direct `config`/`configUrl` inputs take precedence over product resolution; supplying both direct sources is invalid. Product mode needs productId, apiBaseUrl and storeId; variant/collection context participates in resolution.
- `StorefrontResolver` makes credential-free public reads. Unmapped results show fallback content. `LoadPipeline` validates config/URL policy, loads fonts/static images, restores a version-bound draft using `assetMap`, and reports recoverable restore problems. Abort/generation checks discard superseded work and release bitmaps.
- `StateService`, `AssetStore`, `LoadPipeline`, `SaveCoordinator`, and resolver are instance scoped through component providers. Preserve upload cancellation, bitmap cleanup and synchronous computed locks.
- `SaveCoordinator`: freeze/export → emit `customizer-save` with requestId → await matching `saveResult`. Success alone advances the saved baseline. After 30 seconds, retry resends the same request id/payload; stale acknowledgements are ignored. Text change events debounce 150 ms. The element hands persistence to its host; backend customization endpoints do not imply an automatic element save integration.
- `url-policy.ts`, image sniffing, image decoding/crop helpers and font loading enforce asset safety and exportability. Local `idb:` assets are opt-in for embedded use.

## Merchant editing and persistence

- `EditorPageComponent` provides `EditorStore`, `AssetStore`, `MarkupLibrary`; stage/sidebar/inspector consume this session. `EditorStore.edit()` applies immutable `config-edit.ts` transformations, with 100 undo snapshots and 800 ms coalescing. Dirty tracking compares config object identity to the saved baseline. The renderer retains the last validated resolved configuration while raw draft edits are invalid.
- Structural edits must repair cross references, defaults, variant assignments, orphan fields and conditions using existing helpers. `StageComponent` converts pointer coordinates and uses shared rendering beneath its SVG interaction overlay.
- `workspace/configuration-repository.ts` is the UI persistence boundary. Records contain a draft and optional immutable published snapshot. Save checks `expectedUpdatedAt`; publish strictly validates plus checks readiness, snapshots the current version, and advances draft version. Incomplete but structurally valid drafts can be saved. Archiving is separate from publishing.
- `LocalConfigurationRepository` uses IndexedDB, falling back to memory only if opening storage fails; later write failures remain errors. `local-db.ts` uses database `zb-personalizer` version 3 with assets/configs/drafts/cloud-cache/sync/mappings/markups stores. New workspaces are empty; fixtures are explicit dev conveniences.
- Standalone `app.config.ts` selects the configuration repo at creation from `RuntimeConfig` (`window.__ZB_PERSONALIZER__`); standalone mappings/markups remain local. Embedded admin repository adapters choose local/cloud per call, enforce readonly and emit public events.
- `workspace/cloud/ApiClient` handles authenticated HTTP and typed errors. Cloud configuration persistence is authoritative, with best-effort IndexedDB read fallback on network failures and no offline write queue. `AssetSyncService` uploads `idb:`/supported data images using clientRef deduplication and rewrites persisted copies to delivery URLs. `MigrationService` is explicit, resumable and non-destructive.
- `ConfigurationTransferService` embeds local images on JSON export; import validates, upgrades v1, and stores inline images locally. `asset-base.ts` resolves bundled assets relative to the script for embedded admin usage.
- Mapping precedence: variant → product → collection; matching collections sort by externalId. `mapping-resolution.ts` mirrors backend selection. Markups capture area geometry or artwork with fields; insertion is a copy with regenerated ids, cleared source scope/conditions, and font fallback warnings (`markups/markup-edit.ts`).
- Shared styles are in `src/styles/`; customizer styling is component scoped. Admin UI uses `admin/i18n/messages.en.ts` typed keys, French/Arabic catalogs, English fallback and Intl formatting.

## Worker backend

- Separate package `worker-api/`, a Worker dedicated to Product Personalization with its own Postgres database: Hono, Zod, pg through Cloudflare Hyperdrive, R2 or S3 (`aws4fetch`) behind `storage/object-storage.ts`. `src/app.ts` assembles request context/CORS/database, public storefront routes, self-authenticating integrations, then authenticated tenant-scoped merchant routes. Controllers parse HTTP, services implement rules/transactions, repositories own SQL. Code lives in `src/modules/` (`personalization`, `integration-credentials`, `store-settings`, `audit`, `health`).
- Protected API prefix: `/api/v1/plugins/personalization`; public prefix: `/api/v1/storefront/personalization`; signed order events: `/api/v1/integrations/personalization/events`. `app.ts` is the current endpoint inventory; the prefixes are defined in `shared/api-paths.ts` and are a stable contract. Auth derives store from verified JWT or development-only static token, never a client store header. Public storeId identifies a store, not an authorization credential.
- Published mapping resolution excludes unavailable configurations. Storefront service rewrites asset references and refuses unresolved local/relative assets. Public unsigned merchant assets require published references; valid asset HMACs also allow draft delivery. See actual `storefront-service.ts` / `asset-signature.ts` for current behavior rather than older README asset-delivery wording.
- Storage keys are generated under `stores/<store>/product-personalization/{assets,customizations}/`; that segment is stored in every `object_key`, so it must not change. Sniff image contents and enforce size/ownership/reference checks. Customer files have separate private lifecycle/storage access.
- `customization-service.ts`: private shopper uploads produce upload tokens; create resolves the current product mapping, verifies config id and a known configuration version, atomically attaches eligible uploads, and issues a customization access token. Shopper reads/updates need the scoped token; only saved records can be edited. Payload data has structural/size validation, not full server-side field/business evaluation.
- `integration-controller.ts` verifies timestamp and HMAC over exact callback body before parsing; tenant comes from signing credential. Credentials are encrypted and managed only with explicit `integrations:manage` scope (dev exemption). `order-callback-service.ts` transactionally deduplicates event ids, checks product/variant and unique order-line links, and changes saved → ordered; conflicting repeats fail. Only order.confirmed is supported.
- `index.ts` scheduled handler runs `scheduled.ts`, the cleanup job. `cleanup-service.ts` expires abandoned saved customizations, releases files, deletes after grace with retries, and purges tombstones using row locks/claims. Ordered/order-linked customizations and files must survive cleanup. Never wrap storage network calls in database transactions.
- Migrations: one baseline, `0001_baseline.sql`, creating the single `personalization` schema (a store becomes known through its `store_settings` row, created on its first authenticated request; there is no enable flag); append new files. `worker-api/docs/zenbasket-integration.md` documents host integration and explicitly unresolved platform decisions; do not invent those decisions.

## Verification navigation

- Root `package.json`: Angular unit suite (`test:ci`), app build, element build, public declaration consumer (`test:types`). Browser tests use Vitest Node + puppeteer-core + Chrome, built bundles and local static/mock servers; `tests/browser/harness.ts` handles shadow-root hosts. AXE specs cover storefront/admin; other suites cover save protocol, restoration/rendering, embedding/CSP, theme, mapping and admin workflow. Cloud E2E is environment gated.
- Backend `npm run typecheck` and Vitest tests from `worker-api/`. Integration helpers apply migrations and truncate tables in a real disposable PostgreSQL database, using in-memory object storage; inspect helpers before running. Unit tests can be selected separately. Keep integration files sequential to avoid truncate races.
- Do not infer live deployment verification from local tests or documentation. Backend environment secrets, cloud provisioning and host token issuance are external integration concerns.
