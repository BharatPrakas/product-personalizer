# Direct browser-to-storage uploads (R2 and S3)

Files — merchant mockups, artwork, clipart, fonts, and shopper photos / previews / print artwork — go
**from the browser straight to Cloudflare R2 or AWS S3** on a short-lived presigned URL. The Worker
authorizes the upload, then verifies the stored object. It does not carry the file bytes.

The source code is authoritative; this document describes `src/storage/*`,
`src/modules/personalization/direct-upload-service.ts`, `upload-repository.ts` and the `uploads` table in
`migrations/0001_baseline.sql`.

## Architecture

**Before** — every byte crossed the Worker:

```
browser ──POST bytes──▶ Worker ──put──▶ R2 / S3        (validate, hash, store, insert row)
browser ◀── signed Worker URL ── ... ── browser ──GET──▶ Worker ──get──▶ R2 / S3
```

**Now** — the Worker is in the control path only:

```
WRITE
  browser ──1 POST upload-url──▶ Worker ──▶ D1 (uploads: pending) ; presign PUT for ONE staging key
  browser ──2 PUT bytes──────────────────────────────────────────▶ R2 / S3   (pending/<uploadId>)
  browser ──3 POST complete────▶ Worker ──HEAD, read, sniff, SHA-256──▶ R2 / S3
                                  │      copy pending/<id> ─▶ assets/<uuid>.<ext>  (or customizations/)
                                  └──▶ D1 batch: INSERT asset row + uploads → stored   (atomic)

READ
  published merchant asset  browser ──▶ public asset host (CDN)    or  Worker delivery route ──▶ R2 / S3
  private file              browser ──▶ Worker (authorize) ──▶ short-lived presigned GET ──▶ R2 / S3
                                                          or  ──▶ Worker streams it (existing routes)
  config JSON, metadata     Worker ──▶ D1
```

Both providers sit behind one interface (`ObjectStorage`); `STORAGE_DRIVER` picks the adapter and the
service layer, the routes and the Angular client are identical for both.

| Operation | `S3ObjectStorage` | `R2ObjectStorage` |
|---|---|---|
| presigned PUT / GET | SigV4 query signing (`aws4fetch`) against `https://<bucket>.s3.<region>.amazonaws.com` | SigV4 query signing against the **R2 S3 endpoint** `https://<account>.r2.cloudflarestorage.com/<bucket>` (region `auto`) — never a public custom domain |
| HEAD / bounded read / delete | S3 REST | Worker binding |
| promote (copy) | `CopyObject` with `x-amz-copy-source-if-match` | `get` with `onlyIf.etagMatches` → streamed `put` (inside Cloudflare's network) |

A binding cannot mint browser-usable URLs, so R2 needs its own **S3-API token** just for signing; every
other R2 operation keeps using the binding.

## Bucket layout and the pending prefix

One bucket per environment, public and private files separated by key prefix **and** by application
access control (a prefix is not an access control on its own):

```
stores/<store>/product-personalization/
  assets/<uuid>.<ext>             merchant assets   — public only after a PUBLISHED config references them
  customizations/<uuid>.<ext>     PRIVATE customer files — never served publicly
  pending/<uploadId>              INTERNAL staging for direct uploads — never served, listed or referenced
```

Existing `assets/` and `customizations/` keys are unchanged. `pending/` is new and is the **only** key a
presigned PUT can write. The permanent key is generated by the Worker after the bytes are verified, so:

- an object is never visible as an asset until it is verified;
- a leaked or replayed signed URL can touch only a throw-away staging key — it cannot alter an asset that
  was already stored (tested);
- promotion is a conditional copy (ETag), so an object swapped after verification is refused.

## API contract

Errors use the existing envelope `{ "error": { "code", "message", "details?", "requestId" } }`.

### Merchant (authenticated; the store comes from the verified token, never the body)

`POST /api/v1/plugins/personalization/assets/upload-url`

```json
{ "filename": "mockup.png", "contentType": "image/png", "size": 245678, "purpose": "merchant-asset",
  "configId": "cfg-123", "clientRef": "idb:abc", "sha256": "<hex, optional>", "uploadId": "<renew, optional>" }
```

`201`:

```json
{ "data": { "uploadId": "…", "assetId": "…", "status": "pending",
            "uploadUrl": "https://…/stores/<store>/product-personalization/pending/<uploadId>?X-Amz-…",
            "method": "PUT", "headers": { "Content-Type": "image/png" }, "expiresIn": 300 } }
```

- `contentType`: PNG, JPEG, WebP; fonts WOFF2/WOFF/TTF/OTF (several spellings) or `application/octet-stream`
  for a font the browser could not type. Anything else → `415`. `size` ≤ `MAX_UPLOAD_BYTES` else `413`.
  `purpose` is currently only `merchant-asset`.
- `clientRef` makes it idempotent: a retried initiation re-uses the open upload (fresh URL, same
  `uploadId`/`assetId`); a ref that already has a stored asset answers `200` with
  `{ "status": "stored", "uploadUrl": null, "asset": {…} }` and nothing to upload.
- `uploadId` renews the URL of a still-open upload (same file only; else `409 conflict`).
- More than `MAX_OPEN_UPLOADS_PER_STORE` (500) unconfirmed uploads → `429 too_many_open_uploads`.
- `503 direct_upload_not_configured` when presigning credentials are missing (R2: see below).

The browser then does `fetch(uploadUrl, { method: 'PUT', headers, body: file })` — exactly those headers.

`POST /api/v1/plugins/personalization/assets/complete` — `{ "uploadId": "…" }` → `200`:

```json
{ "data": { "assetId": "…", "id": "…", "uploadId": "…", "objectKey": "stores/<store>/product-personalization/assets/<uuid>.png",
            "status": "stored", "contentType": "image/png", "size": 245678, "sizeBytes": 245678,
            "width": 1200, "height": 800, "checksumSha256": "…", "deliveryUrl": "…signed Worker URL…", "publicUrl": null } }
```

`publicUrl` is `null` for a merchant upload: it is not public until a published configuration references it
(then the storefront serves it from the public host if one is configured). `deliveryUrl` is the existing signed
Worker URL, used by the editor for drafts.

| Status / code | Meaning |
|---|---|
| `409 upload_missing` | the object is not in storage yet — `PUT` (again) and retry |
| `409 upload_in_progress` | another request is verifying this upload — retry shortly |
| `422 upload_rejected` + `details.reason` | terminal: `size_mismatch`, `content_type_mismatch`, `invalid_content`, `checksum_mismatch`, `image_dimensions`, `object_changed` |
| `410 upload_expired` | the URL lapsed unconfirmed and cleanup reaped it — start a new upload |
| `503 storage_unavailable` | provider hiccup; the upload stays retryable |
| `404` | unknown upload **or another store's** upload (indistinguishable) |

Completion is idempotent and safe under concurrency: repeating it returns the same asset; N parallel calls
create exactly one asset.

`GET /assets/:assetId/url` → `{ "data": { "url": "<presigned GET>", "method": "GET", "expiresIn": 60 } }`.
Generated per request, `Cache-Control: no-store`, never stored. The existing Bearer-protected
`GET /assets/:assetId/content` still streams through the Worker.

### Shopper (public and anonymous — `?storeId=` names a known store, as for every shopper route)

No merchant login and no token: the Worker checks the store key, rate limits, the per-store open-upload cap and the file contents. The `uploadId` / `assetId` are unguessable UUIDs only the uploader has seen.

`POST /api/v1/storefront/personalization/uploads/url?storeId=…`
`{ "kind": "upload|preview|artwork", "contentType": "image/png", "size": 1234, "filename"?, "sha256"?, "uploadId"? }`
→ `201` `{ uploadId, assetId, uploadUrl, method, headers, expiresIn }`.
Images only (PNG/JPEG/WebP). Passing the `uploadId` of a still-open customer upload renews its URL.

`POST …/uploads/complete?storeId=…` with `{ "uploadId" }` →
`200` `{ assetId, kind, contentType, sizeBytes, width, height }` — the same shape the proxied upload returns, so
attaching (`POST /customizations`, `assets: [{ assetId }]`) is simple. An unknown upload id (or another store's) → `404`.

Only a **verified** upload has a `customization_assets` row (status `uploaded`), so a customization cannot
claim an unverified file: saving with an unconfirmed `assetId` fails with `409 asset_unavailable` and commits
nothing (the existing `pending_attach_count` trigger guard is untouched).

The merchant `GET /customizations/:id/assets/:assetId/url` returns a 60 s presigned GET for an *attached* file;
the merchant streaming route remains. Shoppers have no read route for their files: the one public read is the
customized image (an attached `preview`) at `…/customization-images/:assetId?storeId=…`, see the README.

## Upload lifecycle, retries and idempotency

`uploads.status`: `pending` → `uploaded` (HEAD saw the object) → `verifying` (one request owns it) →
`stored` | `failed`; `expired` is set by cleanup. Transitions are conditional `UPDATE`s whose row count
decides the winner (D1 has no row locks or interactive transactions); the asset insert and the final
`stored` flip are one atomic `batch()`, and the insert is gated on the upload still being `verifying`.

| Situation | Behaviour |
|---|---|
| browser PUT failed / dropped | client retries the PUT with backoff |
| signed URL expired (403) | client asks for a fresh URL for the **same** `uploadId` (no second asset) |
| response to `complete` lost | client repeats `complete`; same asset returned |
| PUT succeeded, confirm failed | the object waits in `pending/`; `complete` can be retried until cleanup reaps it (URL expiry + `PENDING_UPLOAD_GRACE_MINUTES`) |
| browser refresh mid-upload | re-initiate with the same `clientRef` (merchant): same upload, fresh URL |
| two tabs / retries concurrently | one verifies, others get `upload_in_progress` or the finished asset |
| Worker died mid-promotion | a `verifying` claim older than 1 h is retaken; `final_key` was recorded before the copy, so it promotes to the **same** key |
| provider error during verification | claim handed back, `503 storage_unavailable`, retryable |
| object changed after verification | conditional copy fails → `422 object_changed`, staging object deleted |

Verification never trusts the browser: HEAD size must equal the declared size; the stored `Content-Type`
must equal the signed one; the real bytes must sniff as a supported image/font **of the declared type**;
width/height must be > 0 and ≤ 100 megapixels; the SHA-256 is computed server-side (and must match
`sha256` if the client sent one). ETag is **not** used as a checksum.

## Public and private delivery

- **Private by default.** Customer files (`customizations/`) are never public. Merchant assets are served to
  the public only when a **published** configuration references them (`getServableAsset`), or to a holder of
  the HMAC-signed URL (drafts).
- **Default (no public host):** published assets are served by the Worker route
  `GET /api/v1/storefront/personalization/assets/:id` with `Cache-Control: public, max-age=86400,
  s-maxage=604800`. Note: a Worker's own response is not edge-cached automatically; if repeat reads matter,
  set `ASSET_PUBLIC_BASE_URL` (below) or add Cache API caching to that route (not implemented).
- **Optional public asset host (`ASSET_PUBLIC_BASE_URL`):** the storefront config response rewrites a
  published asset to `<base>/<object key>`, so repeat image reads bypass the Worker and ride the CDN.
  Drafts and unreferenced uploads are **never** addressed on this host (the editor keeps the signed Worker
  URL). Previously saved `<base>/<key>` references still resolve.
  **The host must expose only `stores/*/product-personalization/assets/*`.**
  - *R2:* do **not** attach a custom domain to the bucket (it would publish `customizations/` and
    `pending/` too). Front it with a Cloudflare Worker/route that maps only the `assets/` prefix, or leave
    the setting empty.
  - *S3:* keep **Block Public Access on**; use CloudFront with **Origin Access Control** and a behavior/path
    pattern (or CloudFront Function returning 403) that allows only `stores/*/product-personalization/assets/*`.
  - Residual: that host serves any `assets/` object whose (random UUID) key is known, published or not —
    "unlisted URL" semantics. Use the Worker route if that is unacceptable.
- **CORS for canvas:** public asset responses already carry `Cross-Origin-Resource-Policy: cross-origin` and
  `Access-Control-Allow-Origin: *` on the Worker route; set an equivalent CORS rule on the public host.
- **Private reads:** the merchant `…/url` endpoints return a presigned GET (60 s, `PRIVATE_URL_TTL_SECONDS`, max 900 s)
  after the same authorization as the streaming route. Presigned GETs are not stored.

## Cloudflare R2 setup

1. **Bucket** — the existing one (`zb-personalization-assets-<env>`), bound as `PERSONALIZATION_ASSETS`.
   Keep it **without** a public custom domain / `r2.dev` access.
2. **API token (S3 credentials)** — Cloudflare dashboard → R2 → *Manage API tokens* → create a token with
   **Object Read & Write**, scoped to **this one bucket**. Record the *Access Key ID* and *Secret Access Key*.
3. **Worker configuration**

   ```jsonc
   // wrangler.jsonc  (vars are not secret)
   "vars": { "STORAGE_DRIVER": "r2", "R2_ACCOUNT_ID": "<32-char account id>", "R2_BUCKET_NAME": "<bucket>" }
   ```

   ```bash
   wrangler secret put R2_ACCESS_KEY_ID     --env <env>
   wrangler secret put R2_SECRET_ACCESS_KEY --env <env>
   # EU-jurisdiction bucket: also set R2_S3_ENDPOINT=https://<account>.eu.r2.cloudflarestorage.com
   ```

   Locally put the three non-binding values in `.dev.vars`. Presigned URLs target
   `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com/<R2_BUCKET_NAME>/<key>`.
4. **Bucket CORS** (browsers `PUT`/`GET` the bucket cross-origin). The storefront is embedded in many
   custom domains, and a bucket's CORS list is static, so the chosen design is a wildcard origin on a
   **private** bucket — see [Why a wildcard origin](#why-a-wildcard-origin-is-acceptable-here). Apply with
   `wrangler r2 bucket cors set <bucket> --file r2-cors.json`:

   ```json
   { "rules": [{
       "allowed": { "origins": ["*"], "methods": ["PUT", "GET", "HEAD"], "headers": ["content-type"] },
       "exposeHeaders": ["ETag"],
       "maxAgeSeconds": 3600
   }] }
   ```

   (Dashboard equivalent: bucket → *Settings → CORS policy*, fields `AllowedOrigins`, `AllowedMethods`,
   `AllowedHeaders`, `ExposeHeaders`, `MaxAgeSeconds`.) A rule change can take a few seconds to reach
   every edge: right after setting it, a preflight may briefly answer 403 before settling on 204.
   Verify with a preflight against a freshly issued URL (see staging step 4).

## AWS S3 setup

1. **Bucket** — private, **Block Public Access = on**, no bucket policy granting public reads.
2. **IAM user per environment**, least privilege, scoped to the bucket:

   ```json
   { "Version": "2012-10-17", "Statement": [
     { "Effect": "Allow", "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
       "Resource": "arn:aws:s3:::<bucket>/stores/*" },
     { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::<bucket>" }
   ] }
   ```

   `s3:ListBucket` is **required**: without it S3 answers a HEAD for a missing key with 403 instead of 404,
   and the Worker could not tell "not uploaded yet" from "forbidden". Presigned URLs carry this user's
   permissions, so keep it narrow. Use long-term keys (temporary `ASIA…` credentials expire and so would every
   presigned URL signed with them).
3. **Worker configuration** — `STORAGE_DRIVER=s3`, `S3_BUCKET`, `S3_REGION` (vars);
   `wrangler secret put AWS_ACCESS_KEY_ID|AWS_SECRET_ACCESS_KEY --env <env>`.
4. **Bucket CORS** (`aws s3api put-bucket-cors --bucket <bucket> --cors-configuration file://cors.json`) —
   same reasoning and rule as R2:

   ```json
   { "CORSRules": [{
     "AllowedOrigins": ["*"],
     "AllowedMethods": ["PUT", "GET", "HEAD"],
     "AllowedHeaders": ["content-type"],
     "ExposeHeaders": ["ETag"],
     "MaxAgeSeconds": 3600
   }] }
   ```

### Why a wildcard origin is acceptable here

Storefront uploads come from every store's domain (including custom domains), so no static origin list can
be right. The decision is `AllowedOrigins: ["*"]` on a **private** bucket, which is safe because CORS is not
the access control in this design:

- Every browser request to the bucket needs a **presigned URL**, valid for one key, one method and one
  Content-Type for minutes. Without one the bucket answers 403 whatever the origin. The bucket must stay
  private (no `r2.dev` access, no public custom domain, S3 Block Public Access on).
- URLs are minted only by the Worker, which still enforces authentication (merchant) or a known store key
  + rate limits + the open-upload cap (shopper) **at issuance**. Shopper issuance is anonymous, so the
  Worker bounds what it can do rather than who may ask: type/size are signed into the URL and the bytes are sniffed at completion.
- The client sends `credentials: 'omit'`, so no cookies or ambient credentials are involved.
- `*` only lets a browser page *read the response* of a request that already carries a valid signature.

This deliberately relaxes the "no unrestricted production CORS" guideline; the controls that remain are the
signature, its short expiry, issuance-time authorization and the verification at completion. If your
policy forbids `*`, the alternative is exact origins for the admin app and the proxied shopper route
(`LEGACY_PROXY_UPLOADS` stays on), which puts shopper bytes back through the Worker.

## Angular integration

| File | Role |
|---|---|
| `src/app/customizer/util/direct-upload.ts` | Provider-agnostic core: `uploadDirect(blob, gateway, options)`; `DirectUploadError`; `UploadDeduper` |
| `src/app/workspace/cloud/api-client.service.ts` | Merchant gateway: `ApiClient.uploadAsset(blob, opts)` (same signature as before) |
| `src/app/customizer/services/customization-persistence.service.ts` | Shopper gateway: `CustomizationPersistence.upload(...)` (same result shape) |
| `src/app/workspace/cloud/asset-sync.service.ts` | Unchanged contract; adds concurrent-ref de-duplication and `signal` |

Components are untouched: `AssetSyncService`, `CloudFontRepository` and the customizer keep calling the same
methods. The browser only ever sees *a URL, a method, headers and an upload id*; the Worker's `STORAGE_DRIVER`
decides what is behind them.

`UploadOptions`: `signal` (AbortController cancellation), `onProgress` (switches the PUT to XMLHttpRequest,
because `fetch` cannot report upload progress), `putTimeoutMs` (default 120 s), `maxAttempts` (3),
`retryDelayMs` (500, doubling). Behaviour: transient network/5xx/timeout retried with backoff; an expired URL
renewed for the same upload; a lost confirmation repeated; an object that never arrived re-sent; a rejected
file never retried; cancellation aborts the PUT and never confirms. `DirectUploadError.code` is one of
`aborted | network | timeout | url-expired | rejected | unsupported | too-large | rate-limited | unauthorized |
not-configured | storage | confirm-failed | unknown`; messages never contain URLs or keys.

A configuration is only saved after `uploadAsset` resolves, which happens only after the Worker verified the
file; the Worker additionally refuses a draft or publish that references a pending/failed upload
(`422 upload_unverified`). If the Worker answers `503 direct_upload_not_configured` the client falls back to
the legacy proxied route, so an environment without presigning credentials keeps working.

## Cleanup

`CleanupService` (hourly cron) gained three idempotent phases (counters in `cleanup_runs`):

1. `expire_pending_uploads` — `pending`/`uploaded` uploads whose URL expired more than
   `PENDING_UPLOAD_GRACE_MINUTES` (30) ago become `expired`; dead `verifying` claims are handed back.
2. `delete_upload_objects` — once the URL has certainly expired, deletes each finished upload's
   `pending/` object (also for `stored` uploads: a replayed PUT may have re-created it). For `failed`/`expired`
   uploads it also deletes a promoted copy **only if no `assets`/`customization_assets` row references it**.
   Keys outside the store's expected prefixes are refused. Failures keep the row for the next run
   (`cleanup_attempts`, `last_error`).
3. `purge_upload_records` — drops fully cleaned records older than `EXPIRED_TOMBSTONE_DAYS`.

Existing behaviour is unchanged: referenced merchant assets are never touched; attached or ordered customer
files are preserved; `pending_attach_count` is not involved.

## Security notes and known limits

- **Size is enforced after upload, not by the signature.** The signed headers are `content-type` and `host`;
  a browser cannot set `Content-Length`, so the provider cannot reject an oversized PUT up front. A client
  can therefore write an object larger than declared to `pending/` within the 5-minute URL window; it is
  caught at completion (HEAD size ≠ declared), never promoted, and deleted by cleanup. Bound exposure with
  `UPLOAD_URL_TTL_SECONDS`, `MAX_OPEN_UPLOADS_PER_STORE`, and edge rate limits.
- **Rate limits.** Storefront write routes use the existing per-store+IP limiter (in-memory per isolate).
  Add Cloudflare rate-limiting rules for `POST …/uploads/url`, `…/uploads/complete`, `…/assets/upload-url`
  and `…/assets/complete` (suggestion: 30 requests/min/IP on the storefront paths).
- **Anonymous shopper uploads** are bounded by the store key, rate limits and the
  open-upload cap; there is no per-shopper identity before the first save (unchanged from the proxied flow).
- **Verification reads the object into the Worker** (≤ `MAX_UPLOAD_BYTES`, 15 MB) to sniff and hash it —
  server-side, not a proxy of the upload — which costs memory/CPU per completion.
- **Presigned URL reuse:** a URL is valid for its exact key, method and Content-Type until expiry; replays
  can only recreate `pending/<uploadId>` (cleaned up). Tested.
- **Bucket CORS is a wildcard** because storefront origins are per store and a bucket's list is static;
  see [Why a wildcard origin is acceptable here](#why-a-wildcard-origin-is-acceptable-here). Keep the bucket private.
- **Public host (`ASSET_PUBLIC_BASE_URL`)** serves by key with unlisted-URL semantics (see above).
- **Credential scope:** the R2 token / IAM user can read and write the whole bucket's `stores/*`; per-tenant
  isolation is enforced by the Worker (server-generated keys, store-scoped queries), not by the credential.
- Error messages never include keys, URLs or provider bodies; provider error *codes* are logged server-side.
- The R2 and S3 live paths were **not** exercised against real accounts in this change (see Testing).

## Backward compatibility and migration

- The `uploads` table and three counters on `cleanup_runs` live in `migrations/0001_baseline.sql` (folded in
  while only the dev environment existed, so a database created from it has them from the start). A database
  that already ran an earlier `0001` must be recreated (dev) or given a **new** migration containing the
  `CREATE TABLE uploads …` block and the three `ALTER TABLE cleanup_runs ADD COLUMN …` statements (staging /
  production once they hold data). Apply schema changes **before** deploying the code:
  `wrangler d1 migrations apply <db> --env <env> [--remote]`.
- Existing `assets` / `customization_assets` rows, object keys, signed asset URLs, published configurations
  and the `…/assets/:id/content` routes keep working. Legacy proxied routes (`POST /assets`,
  `POST /storefront/…/uploads`) remain until you set `LEGACY_PROXY_UPLOADS=false` (then they answer `410`).
- One deliberate change: with `ASSET_PUBLIC_BASE_URL` set, a merchant upload's `deliveryUrl` is now the
  signed Worker URL (it used to be `<base>/<key>` for drafts too), and the *published* storefront config
  now points at `<base>/<key>`. Configs that already stored `<base>/<key>` URLs still resolve.
- Roll back by deploying the previous Worker; the extra table is ignored.
- Rolling out: deploy the Worker first, then the Angular build (an old Angular build keeps using the proxied
  routes; a new build against an old Worker would 404 on `…/upload-url`).

## Staging deployment and validation

Nothing here was run against a real account by the author; these are the steps to verify.

1. `wrangler d1 migrations apply zb-product-personalizer-db-staging --env staging --remote`
2. Configure storage (R2 *or* S3 sections above): the wildcard bucket CORS rule; secrets via
   `wrangler secret put … --env staging`; confirm `STORAGE_DRIVER`, bucket vars.
3. `wrangler deploy --env staging`, then deploy the Angular build.
4. **CORS preflight** (use a freshly issued `uploadUrl`; any origin should pass):

   ```bash
   curl -si -X OPTIONS "$UPLOAD_URL" -H "Origin: https://any-store.example.org" \
     -H "Access-Control-Request-Method: PUT" -H "Access-Control-Request-Headers: content-type"
   # expect 204 with Access-Control-Allow-Origin: * and Allow-Methods containing PUT
   ```
5. Run [the example](#a-complete-example) with a small PNG; then check: the asset row is `stored`, the object
   exists under `assets/`, the `pending/` object is gone (or gone after the next cron), `GET …/assets/:id/url`
   downloads the file, and a second `…/complete` returns the same `assetId`.
6. Negative checks: PUT with a different `Content-Type` → 403; PUT after 5 minutes → 403; upload a text file
   named `.png` → `422 invalid_content`; shopper `complete` for another store's `uploadId` → 404.
7. Trigger cleanup: `wrangler dev --test-scheduled` locally, or wait for the cron; `SELECT * FROM cleanup_runs
   ORDER BY started_at DESC LIMIT 3;` shows the new counters. Confirm an abandoned upload becomes `expired`.
8. Add the Cloudflare rate-limiting rules named above.

## A complete example

```bash
API=https://api-staging.example.com/api/v1/plugins/personalization
AUTH="Authorization: Bearer $TOKEN"
FILE=mockup.png; SIZE=$(stat -c%s "$FILE")

# 1. initiate
INIT=$(curl -s -X POST "$API/assets/upload-url" -H "$AUTH" -H 'Content-Type: application/json' \
  -d "{\"filename\":\"$FILE\",\"contentType\":\"image/png\",\"size\":$SIZE,\"purpose\":\"merchant-asset\"}")
URL=$(echo "$INIT" | jq -r .data.uploadUrl); UPLOAD_ID=$(echo "$INIT" | jq -r .data.uploadId)

# 2. upload straight to R2 / S3 (no Authorization header — the signature is the credential)
curl -s -X PUT "$URL" -H 'Content-Type: image/png' --data-binary @"$FILE"

# 3. confirm
curl -s -X POST "$API/assets/complete" -H "$AUTH" -H 'Content-Type: application/json' -d "{\"uploadId\":\"$UPLOAD_ID\"}"
#   -> { "data": { "assetId": "...", "status": "stored", "publicUrl": null, "deliveryUrl": "…?sig=…", ... } }

# 4. use the asset: put data.deliveryUrl in the config (src), save and publish as usual.
#    Reads: published -> storefront config returns the asset URL; private -> GET $API/assets/<id>/url
```
